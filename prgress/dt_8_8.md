# SEC Filings RAG — Project Progress Log

*A plain-language record of what's been built, why, and what's left. Written for future-you to pick back up without re-reading the whole conversation.*

---

## The Project, in One Paragraph

A system where you can ask a plain-English question about a Big Tech company's SEC 10-K annual report (Apple, Microsoft, Alphabet, Amazon, Meta — last 3 years each) and get back a direct, cited answer — instead of reading a 100-200 page document yourself. The standout feature: cross-checking any numbers the AI pulls out against SEC's own official XBRL data, so you can trust the answer is actually correct, not just plausible-sounding.

**Built as a free, fully open-source stack** — no OpenAI key. Deployable, so a real person could try it. Not aiming for "handles a million users," just "works well and looks like real engineering."

---

## The Stack (what we're using and why)

| Piece | Tool | Why |
|---|---|---|
| Backend framework | FastAPI | Modern, fast, great for building APIs |
| Document parsing | Docling | Understands tables/headings, not just raw text |
| Embeddings (turns text into searchable meaning) | BAAI/bge-large-en-v1.5 | Free, strong quality, no OpenAI needed |
| Vector database (stores + searches embeddings) | Qdrant | Free, self-hosted via Docker, good filtering |
| Keyword search | BM25 | Classic exact-word matching, complements embeddings |
| Reranker | BAAI/bge-reranker-large | Improves result ordering after initial search |
| LLM (writes the actual answer) | Groq hosting Llama 3.3 70B | Free, fast, strong enough for accurate numbers |
| Database | SQLite | Simple, file-based, no server needed |
| Evaluation | Ragas | Measures answer quality/faithfulness |

## What's Been Built So Far

### Phase 1 — Planning
Defined the problem, scope (5 companies, 3 years each), and what "success" looks like. Decided this is a portfolio project, not a production system — good, working, and deployable, but occasional imperfection is fine.

### Phase 2 — Backend Setup
- Clean folder structure separating "what things look like" (models), "how to talk to the database" (repositories), "the real logic" (services), and "the outside world's entry point" (api).
- A settings system that refuses to start the app if secrets (passwords, API keys) are missing — a safety net, not a bug.
- The actual FastAPI app skeleton, with a `/health` check (is the app alive?) and `/health/ready` check (can it actually reach the database?).
- Real database tables set up (`User`, `Document`), with a system (Alembic) to track schema changes over time like a version history.

**Real-world lesson learned:** Windows' OneDrive was silently interfering with the project folder, causing mysterious errors. Fixed by moving the whole project to a plain `C:\Dev` folder, away from OneDrive's reach.

### Phase 3 — Repositories
Built the "only way to talk to the database" classes — `DocumentRepository` and `UserRepository` — so no other part of the app writes raw database queries directly. Tested and confirmed working.

### Phase 4 — Fetching Real Filings
Built a tool that talks to SEC's official EDGAR website (a free government data source) to download real 10-K filings. Decided to keep them as HTML (not PDF) since HTML preserves real table/heading structure that a PDF conversion could lose. Successfully downloaded all **15 real filings** (5 companies × 3 years each).

### Phase 5 — Cleaning the Parsed Documents
Discovered that Docling's HTML parsing had two quirks specific to SEC filings:
1. It sometimes treated pure layout/spacing HTML as if it were a real data table (fixed by deleting fully-empty tables).
2. It sometimes duplicated a single value 2-3 times across table cells that were originally merged (fixed by de-duplicating repeated text).

**Important catch:** an early, more aggressive cleaning idea (deleting any "mostly empty" table) would have accidentally deleted real financial numbers, since actual revenue tables also have lots of blank spacer cells. Caught this before it caused silent data loss, and used the safer, narrower rule instead.

### Phase 6 — Finding Sections ("Item 1", "Item 7", etc.)
SEC filings don't use "real" HTML headings — everything looks like plain text to a computer. Built logic to detect the Item-numbered sections (Item 1, Item 1A, Item 7...) by recognizing the pattern, and to tell the difference between the real section heading and the same text appearing earlier in the Table of Contents (a real section has its title written on the same line; a Table of Contents entry doesn't). Verified: correctly found all 23 real sections in a test filing, with zero duplicates.

### Phase 7 — Chunking
Split each section's content into small, focused pieces ("chunks") — small enough for accurate search, but not so small they lose context. Tables always become their own complete chunk (never split in half, since a partial table is close to useless). Built a real `DocumentChunk` database table to permanently save these chunks (not just print them and lose them).

### Phase 8 — Embeddings
Converted chunk text into vectors (long lists of numbers that capture meaning, not just words) using the `bge-large` model, running for free on your own CPU.

### Phase 9 — Vector Storage (Qdrant)
Set up Qdrant (running via Docker) to store those vectors, linked back to their matching database rows. Ran a real search test — asked "What products does Apple sell?" and got back genuinely correct, well-ranked answers, proving the whole pipeline (parse → clean → tag → chunk → embed → store → search) actually works end to end.

## Currently Running

Scaling everything above from "just one test document" to **all 15 real filings** — running the full pipeline (parse → clean → tag → chunk → embed → store) in one batch job. This takes a while on CPU (expect it to run for a good chunk of time), and it's designed to be safe to re-run if it fails partway — already-processed filings get skipped automatically.

## What's Left (Roadmap)

- **Hybrid search** — combining keyword search (BM25) with the meaning-based search we already have
- **Reranking** — using the `bge-reranker-large` model to improve result ordering after initial search
- **Prompt engineering + RAG pipeline** — actually having the LLM (Groq/Llama) write a real answer using retrieved chunks, with citations
- **Evaluation (Ragas)** — measuring how accurate/faithful the answers actually are
- **XBRL cross-validation** — the differentiating feature: checking extracted numbers against SEC's official structured data
- **Authentication** — real login system (models already built, not wired up yet)
- **React frontend** — the actual user-facing website
- **Docker + deployment** — packaging the whole app to run somewhere real people can use it
- **Advanced RAG techniques** (optional, later) — things like Contextual Retrieval, Multi-Query Retrieval, HyDE

---

*Approach throughout: build one small piece at a time, test it against real data before moving on, and when something looks wrong, dig in and understand why rather than guessing. This caught several real bugs before they became bigger problems (table duplication, Table-of-Contents false positives, the near-miss with deleting real financial data).*
